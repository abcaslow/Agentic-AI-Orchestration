[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] How Collection Works
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] In order for ITPIE to analyze your network, it must connect to and gather information from it. Unfortunately, many vendors do not (or did not) build programmatic interfaces for products like ITPIE.
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] When possible on modern technologies, ITPIE uses custom collectors tailored to vendors’ specific APIs or other programmatic access methods. For example, the Amazon AWS collector does not "scrape" the AWS console — it connects to Amazon’s API and gathers information the same way their own tools do.
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] For devices and technologies that only had human operators in mind, ITPIE utilizes proprietary parsing techniques to view your network the same way an administrator would. Most commonly, this is via the SSH (secure shell) protocol.
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] ITPIE uses carefully crafted "parsers" that are able to read through the unstructured text of SSH terminals and translate it to an internal model.
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] This document describes how the SSH collection process works.
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] Glossary
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] Term Description
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] parent command A command that gathers information used to generate a different command. Example: show interfaces
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] child command A templatized command that uses information gathered from a parent command. Example: show interface %value%
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] regular command A command that does not imply either a parent or child relationship. Example: show running-config
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] identification command A command primary associated with the Identification stage (but might also be needed during regular collection.) Example: show version
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] fingerprint command A command primarily associated with the Fingerprint stage (but might also be needed during regular collection.) Example: show serial-number
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] VOMV Vendor, operating system, model, and version: ITPIE’s internal name for the concept of "make, model, and trim."
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] virtual system ITPIE’s internal name for network devices that have a virtualization/logical configuration concept (such as Cisco’s ASA platform.)
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] Authentication
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] The first step to gathering any information from the network is connecting to it and the administrator of the ITPIE instance must be able to provide suitable authentication credentials to do so. The credentials provided must have the requisite level of access for ITPIE to function.
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] ITPIE will try credentials until it successfully gets a command prompt. It will then store which credential worked for a particular device in the future. This technique reduces the chance of account lockouts by ensuring the correct credential is picked first once it is known.
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] Elevation
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] Many vendors allow authentication credentials to have varying levels of access, which may or may not have sufficient access for ITPIE to function.
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] If the network is configured to prevent authentication credentials from automatically providing a high enough level of authorization, ITPIE may need to perform some kind of elevation procedure. For example, on Cisco equipment, this would be accomplished by executing the "enable" command and then completing an additional authentication process.
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] ITPIE’s SSH collector has configurable strategies for this process but the default is generally successful. This phase of collection is optional and happens only when "privileged credentials" have been configured for this job’s targets.
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] Once the device has responded affirmatively to the elevation process, ITPIE is able to proceed on to the Identification process.
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] Identification
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] ITPIE starts off knowing very little about a device; no different than a human operator when first connecting to an unknown device. If ITPIE has connected to a particular device in the past, it trusts (but verifies) that the VOMV previously stored is still accurate.
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] In the case of connecting to a device it does know about, the number of identification commands ITPIE executes is greatly reduced. Otherwise, it will run through the full suite.
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] This list of commands is ever-changing as the product evolves but some example commands used to determine basic information about the device are:
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] show version - works across many vendors
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] hostnamectl - works on most Linux-based servers and some network equipment
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] show system - works on various routers/switches
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] The full list is around 60 commands and most devices will simply return a command not found for a great number of them. As ITPIE works through the commands, it parses their output (or lack thereof) and uses that to narrow down the list for future collections. Previously identified devices only need a few commands to verify assumptions.
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] This verification is important because, for example, an administrator might have replaced a network switch with an entirely different product but re-used the same IP address. ITPIE is able to determine that the device is no longer the one it saw previously and will gracefully recover.
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] Fingerprint
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] The final piece of information ITPIE needs is to uniquely identify a given device from others in the network. This is typically done with information gathered in the previous Identification stage. The catalog of fingerprinting commands is rather small as only a handful of vendors require the use of one.
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] In all cases, ITPIE will only proceed if it has successfully found enough information to generate a fingerprint. This is simply the hash of uppercased vendor + a uniqueID (serial number, MAC, UUID, SNMP Engine IA). The exact uniqueID used for the fingerprint depends on the VOMV of the device undergoing collection.
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] Collection
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] At this point in the process, ITPIE has authenticated, has authorization, has a VOMV, and knows the device’s specific uniqueness characteristic (such as serial number). ITPIE can then begin the separate stages of collection listed below.
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] Primary
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] The primary phase of collection executes a large set of commands specific to the VOMV of the device. The output from these commands is parsed and optionally stored.
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] In order, the following kinds of commands are run (tailored to this device based on its VOMV) and the configuration of the collection job (such as MAC-only vs a full collection.)
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] parent commands and regular commands
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] identification commands
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] fingerprint commands
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] As noted in the glossary, ITPIE has a concept of parent/child commands. As a concrete example, Cisco switches have a command that list all known interfaces: show interfaces .
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] Those switches also allow one to query each interface for additional information by use of a command that looks like: show interface %value% where ‘%value%’ is replaced with the interface name. ITPIE calls these interpolated commands "child commands".
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] ITPIE keeps track of these relationships and uses the output of parent commands to generate the new child commands to be executed later.
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] Secondary
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] The secondary collection phase has enough information to run the following types of commands:
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] child commands
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] parent virtual system commands
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] regular virtual system commands
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] The vast majority of the devices will stop at this phase of collection.
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] However, devices with a concept of logical configurations may require additional commands. Some platforms (such as Cisco ASAs) can be split into "contexts". A context on that platform is analogous to a virtual machine or container on a regular server.
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] During Primary collection, ITPIE notices this and keeps track of which contexts existed and will now "crawl" into each virtual system and execute the relevant parent and/oor regular commands.
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] The list of commands executed in each virtual system is the same used during Primary collection. Each virtual system often behaves like an independent piece of network equipment.
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] Virtual System Secondary
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] This is the final phase of collection only occurs on devices with a concept of virtual systems. ITPIE executes the child commands to the previously gathered parent virtual system commands.
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] For example, ITPIE would have entered a context during Secondary and executed show interfaces . Like Secondary child commands, that information would be used to generate a list of commands for this phase, such as show interface Gi0/1 .
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] During both Secondary and Virtual System Secondary, ITPIE enters and exits virtual systems by executing "before" and "after" commands — the same ones an administrator would use during their day-to-day operation of the network. These vary by platform.
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] Analysis
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] After ITPIE has gathered all of the data from the phases listed above for a given device, it then runs this information through a complex series of transformations and computations. This is done on the fly and once complete for a given device, it becomes available in the in the ITPIE:OPS web interface.
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] Once the collection has finished with all of the configured devices, another process is run that generates maps and provides data for network-wide features in the ITPIE:OPS web interface.
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] Primary
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] Once the raw data is captured, it goes through a series of processing steps to normalize the data and remove duplication. This process is entirely inter device, focusing only on getting the device information into normal forms.
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] Secondary
[ITPIE:OPS Documentation | How Collection Works | https://itpie-hostname/documentation/content/features/collection/how-collection-works.html] During secondary analysis we take the normalized device information and we integrate it into the larger data set, deriving properties that require knowlege of device relationships, and performing aggregation level clean up actions.
